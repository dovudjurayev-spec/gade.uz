# Задача: навести строгую иерархию категорий в каталоге gade.uz

Заказчица требует чёткую структуру **Категория → Подкатегория → 2-я подкатегория (если есть)**, максимум 3 уровня.
Сейчас в каталоге (например `/catalog?category=makiyazh`) одна и та же подкатегория («Брови») может выводиться несколько раз,
а часть товаров висит не в тех подкатегориях.

## Контекст проекта
- Next.js 15 (App Router) + TypeScript, Drizzle ORM, Postgres (Neon), Tailwind. Дев-сервер: `localhost:3001`.
- Ключевые файлы:
  - `src/db/schema.ts` — таблица `categories` (adjacency list: `parentId`, `sortOrder`, `isVisible`), `products.categoryId`
  - `src/lib/billz/sync.ts` — импорт товаров из Billz, функция `ensureCategory()`
  - `src/lib/billz/client.ts` — тип `BillzProduct`, поле `categories: { id, name }[] | null`
  - `src/repositories/products.ts` — `listProducts()`, `countProducts()`, `resolveCategoryIds()`, `listCategories()`, `listCategoriesWithProducts()`
  - `src/repositories/types.ts` — `CategoryNode`, `ProductListItem`
  - `src/app/catalog/page.tsx` — вывод каталога и группировка по подкатегориям
  - `src/components/layout/site-header.tsx` — меню разделов
  - `src/app/categories/page.tsx` — страница «Все категории»
  - `src/app/admin/(protected)/**` — админка (управления категориями сейчас НЕТ)
  - `scripts/audit-categories.ts` — существующий read-only аудит категорий

## Гипотезы по причинам (проверь по коду и данным, не принимай на веру)
1. `ensureCategory()` берёт только `p.categories?.[0]` и создаёт узел **всегда корневым** — `parentId` не проставляется никогда.
   Иерархия существует только там, где `parent_id` проставили вручную, и синк её не воспроизводит.
2. Поиск существующей категории идёт **только по `slug`**, без нормализации имени → одноимённые узлы («Брови», «Брови », «БРОВИ»,
   «Брови» из разных веток Billz) плодят дубли строк в `categories`.
3. `resolveCategoryIds()` возвращает категорию + **только прямых детей** → третий уровень выпадет из фильтрации и счётчиков.
4. В `listProducts()` alias `parent_categories` поднимается ровно на один уровень → при 3 уровнях `categoryName`/`categorySlug`
   перестанут быть корнем.
5. Группировка по подкатегориям в `src/app/catalog/page.tsx` делается в JS в пределах одной страницы (48 товаров),
   дедуп идёт по `slug`, а не по канонической сущности, плюс есть хак «слить хвостовую группу с <4 товарами в предыдущую».
   Это вторая причина повторяющихся заголовков.
6. Нет ограничений в БД: ни уникальности `(parent_id, имя)`, ни ограничения глубины, ни защиты от циклов.

## Фаза 0. Аудит — НИЧЕГО НЕ МЕНЯТЬ
Напиши `scripts/audit-category-tree.ts` (read-only, по образцу `scripts/audit-categories.ts`) и выведи отчёт:
- полное дерево категорий с `id`, `parent_id`, `level`, `slug`, `name`, `sort_order`, `is_visible`, кол-вом товаров (всего / видимых);
- дубли по нормализованному имени (`lower(trim())`, NBSP→пробел, `ё`→`е`) — глобально и в пределах одного родителя;
- узлы глубже 3 уровней и циклы;
- товары без категории; товары, висящие на нелистовых узлах;
- категории без товаров;
- сырой JSON поля `categories` из Billz для 20 произвольных товаров — нужно понять, это упорядоченный путь
  («Макияж», «Брови», «Карандаши») или параллельные теги. От этого зависит вся логика синка.

Сохрани результат в `docs/category-audit.md`. **Остановись и покажи мне отчёт до перехода к Фазе 1.**

## Фаза 1. Модель данных
Миграция через `npx drizzle-kit generate` (существующие миграции не редактировать):
- `categories`: добавить `level` (smallint, 1..3), `path` (text, слаг-путь вида `makiyazh/brovi/karandashi`, уникальный),
  `billz_category_id`, `is_locked` (boolean — ручная расстановка, синк её не перетирает);
- уникальный индекс на нормализованное имя в пределах родителя: `(coalesce(parent_id,0), lower(btrim(name)))`;
- CHECK `level between 1 and 3`; проверка `parent.level = level - 1` (триггер или проверка в коде + тест);
- `products.category_id` = **всегда лист** (самый глубокий узел ветки). Никаких «товар на корне», если у корня есть дети —
  если такие есть, они переезжают в подкатегорию «Другое» внутри своего корня;
- новая таблица `category_aliases (billz_name_normalized unique, category_id)` — чтобы разовые правки распределения
  переживали синхронизацию.

## Фаза 2. Репозиторий
- `resolveCategoryIds()` → рекурсивная выборка всех потомков (recursive CTE или `path LIKE 'makiyazh/%'`), работает на 3 уровня;
- `getCategoryTree()` — одно обращение к БД, отдаёт дерево `root → sub → subsub` с числом видимых товаров на каждом узле;
- `ProductListItem` дополнить полями `rootCategory`, `subCategory`, `leafCategory` (каждое `{id, slug, name}` или `null`);
- добавить `getCategoryBreadcrumbs(slug)`;
- сортировка товаров: по `(root.sort_order, sub.sort_order, leaf.sort_order, product.name)`, чтобы группы никогда не разрывались.

## Фаза 3. Синхронизация с Billz
- `ensureCategory()` заменить на `ensureCategoryPath(names: string[])`: идёт по пути, на каждом уровне ищет узел
  по `(parentId, нормализованное имя)`, при отсутствии создаёт с корректными `parentId`, `level`, `path`;
- нормализация имени: trim, схлопывание пробелов, NBSP → пробел, `ё`→`е`, casefold; slug формировать из полного пути,
  чтобы не плодить `-1`, `-2`;
- товар привязывается к **самому глубокому** узлу пути;
- если у товара несколько категорий и это не путь, а теги — правило выбора вынести в одну функцию с комментарием
  и логировать спорные случаи;
- сначала проверить `category_aliases`;
- узлы с `is_locked = true` синк **не переподвешивает и не переименовывает**;
- новые неизвестные узлы Billz кладутся под служебный корень «Новые из Billz» (скрытый, `is_visible = false`)
  и попадают в отчёт `sync_log`, а не сыпятся в витрину.

## Фаза 4. Разовая чистка данных
Скрипт `scripts/fix-category-tree.ts` с флагом `--dry-run` **по умолчанию** и явным `--apply`:
1. слить дубли (одинаковое нормализованное имя у одного родителя): оставить узел с наибольшим числом товаров,
   переподвесить товары и детей, остальные удалить;
2. переподвесить корневые узлы, которые на самом деле подкатегории (по образцу с сайта: Брови, Глаза, Губы, Лицо,
   Подарочный набор → Макияж), используя редактируемый файл соответствий `data/category-map.json`;
   **структуру дерева не выдумывай** — сгенерируй предлагаемый `category-map.json` из данных и покажи мне на утверждение;
3. перед `--apply` сделать дамп таблиц `categories` и `products` в `backups/` (CSV или pg_dump);
4. после прогона вывести отчёт: что слито, что перенесено, сколько товаров сменило категорию.
