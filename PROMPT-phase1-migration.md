# Фаза 1: инварианты категорий в БД (gade.uz)

Продолжаем работу над иерархией Категория → Подкатегория → 2-я подкатегория (максимум 3 уровня).
Фаза 0 (аудит) завершена, отчёт в `docs/category-audit.md`. Фикс A закоммичен: `ea7e41d fix(billz-sync):
preserve manual category/brand assignments on update`. Незакоммиченный черновик Фаз 2/5 сохранён в ветке
`wip/catalog-l2-grouping` — **в этой фазе её не трогаем**.

## Исходные данные из аудита
- 27 категорий: 6 корневых (Макияж, Ногти, Уход за лицом, Аксессуары, Уход за телом, Парфюмерия) + 21 на 2-м уровне.
- Циклов нет, глубже 3 уровней нет, дублей имён нет — ни глобально, ни внутри родителя.
- 1 товар на нелистовом узле: «Брелок» привязан к «Аксессуары», у которых есть дети.
- 1694 товара всего, из них видно на сайте ~400–500 (показываются только позиции с остатком).
- Товаров без категории: 18 видимых, ~103 всего.
- Billz отдаёт плоский одиночный тег (6 имён = наши корни), иерархии там нет. Источник истины — наш сайт.

## Что сделать

### 1. Схема (`src/db/schema.ts`)
В таблицу `categories` добавить:
- `level` smallint NOT NULL DEFAULT 1 — 1..3;
- `path` text — слаг-путь вида `makiyazh/brovi/karandashi`, уникальный;
- `billz_category_id` varchar(64) — id узла из Billz, если известен;
- `is_locked` boolean NOT NULL DEFAULT false — ручная расстановка, синк её не перетирает.

Новая таблица `category_aliases`:
- `id` serial PK, `billz_name_normalized` varchar(200) NOT NULL UNIQUE, `category_id` integer NOT NULL
  REFERENCES categories(id) ON DELETE CASCADE, `created_at` timestamptz NOT NULL DEFAULT now().

Нормализация имени (единая функция в коде, переиспользуется в Фазе 3): trim → схлопывание пробелов →
NBSP (U+00A0) в обычный пробел → `ё` в `е` → lower.

### 2. Ограничения
- `CHECK (level BETWEEN 1 AND 3)`;
- уникальный индекс на нормализованное имя в пределах родителя:
  `CREATE UNIQUE INDEX categories_parent_name_uniq ON categories ((COALESCE(parent_id, 0)), lower(btrim(name)));`
- уникальный индекс на `path`;
- целостность `level` и `path`: триггер `BEFORE INSERT OR UPDATE`, который вычисляет `level = parent.level + 1`
  и `path = parent.path || '/' || slug`, отклоняет `level > 3` и отклоняет цикл (родитель не может быть
  собственным потомком). При смене `parent_id` или `slug` узла триггер должен рекурсивно пересчитать
  `level` и `path` у всех потомков — иначе после первого же переноса в админке пути разъедутся.

Инвариант «`products.category_id` всегда указывает на лист» в этой фазе **не форсируем на уровне БД** —
сначала надо перенести «Брелок» (Фаза 4-lite). Пока проверяем его в `scripts/audit-category-tree.ts`.
Отдельной миграцией добавим позже, когда нарушений будет ноль.

### 3. Бэкфилл для 27 существующих категорий
- `level`: 1 для `parent_id IS NULL`, 2 для остальных (глубже 3 нет — подтверждено аудитом);
- `path`: для корней = `slug`, для детей = `parent.slug || '/' || slug`;
- `is_locked = true` для всех 27 существующих узлов: текущее дерево расставлено вручную и синк не должен
  его трогать;
- `billz_category_id` заполнить для 6 корневых узлов, если id из Billz есть в отчёте аудита; иначе оставить NULL.

**Перед применением** выведи таблицу: id, parent_id, slug, name → вычисленные level и path для всех 27 строк,
и покажи мне. Ничего не применяй, пока не подтвержу.

### 4. Механика миграции
- Сгенерируй через `npx drizzle-kit generate`. Существующие миграции не редактируй.
- Выражения-индексы, CHECK и триггер drizzle-kit сам не сгенерирует — допиши их SQL-файлом миграции руками
  и объяви в схеме так, чтобы следующий `generate` не пытался их удалить.
- Бэкфилл — частью той же миграции, после добавления колонок и до создания уникальных индексов.
- Обнови `CategoryNode` в `src/repositories/types.ts` (`level`, `path`), но **логику выборок в этой фазе не меняй** —
  рекурсивные запросы это Фаза 2.

### 5. Проверка
- `npm run typecheck` и `npm run build` без ошибок;
- прогнать миграцию сначала на отдельной ветке Neon (не на проде) и на ней же прогнать
  `scripts/audit-category-tree.ts` — дерево должно остаться идентичным, `level` и `path` заполнены у всех 27 строк;
- проверить триггер тестами прямо в SQL на ветке Neon: попытка создать 4-й уровень падает; перенос узла
  пересчитывает path у детей; попытка сделать узел собственным потомком падает; вставка дубля имени
  у того же родителя падает, а у другого родителя проходит;
- откат: убедиться, что `down`-путь (или явный rollback-скрипт) есть и проверен.
