## 1. Роль и задача

Ты — senior full-stack разработчик, специализирующийся на e-commerce для рынка Узбекистана.

Твоя задача — спроектировать и разработать интернет-магазин **gade.uz** для официального дистрибьютора профессиональной косметики **GADE** в Узбекистане.

Ключевой принцип, которому подчинены все решения: **максимально простой путь от входа на сайт до оформленного заказа.** Если какой-то элемент не помогает пользователю купить — его не должно быть.

## 3. Референс

Заказчику нравится сайт **aestheticcosmetics.store** — он должен быть взят за основу по UX-логике и уровню исполнения.

Что конкретно перенести:

- **Структура:** Главная → Каталог с фильтрами → Карточка товара → Корзина → Оформление в один экран
- **Навигация:** минимум пунктов в шапке (Каталог, Подбор, О компании, FAQ) + иконки избранного и корзины
- **Главная страница:** hero-баннер с одним чётким CTA → плитка категорий → блок бестселлеров → блок доверия («только оригинал», «доставка по Ташкенту», «возврат 14 дней», «гарантия качества») → наборы/подарки → блок о компании с адресом, телефоном, картой и соцсетями
- **Квиз «Подбор ухода»** — 3 коротких вопроса, на выходе подборка товаров. Сильный инструмент конверсии для покупателя, который не разбирается в профессиональной косметике
- **Карточка товара:** крупное фото, линейка бренда, объём, цена (со старой ценой при скидке), статус наличия, кнопка «В корзину» на первом экране без скролла
- **Тон текстов:** человеческий, объясняющий пользу, без маркетингового шума

Что улучшить относительно референса:

- Быстрое оформление заказа **без обязательной регистрации** (гость → телефон + имя + адрес → готово)
- Отправка заказа в Telegram-бот менеджера в момент создания
- Живые остатки из Bitrix вместо ручного проставления «нет в наличии»

## 4. Хостинг и инфраструктура

**Обязательное требование заказчика: сайт размещается в сети TAS-IX, на серверах aHOST (ahost.uz), домен gade.uz.**

Причина: трафик внутри TAS-IX для узбекистанских пользователей бесплатный и в разы быстрее внешнего. Вся аудитория магазина находится в Узбекистане, поэтому размещение основного приложения за рубежом (Vercel, дата-центр в Германии) исключено.

Схема проверена на боевом проекте aestheticcosmetics.store — тот же хостинг, Next.js под Node.js Selector в cPanel.

### Что заказываем

| Позиция | Тариф | Стоимость |
|---|---|---|
| Хостинг | **aHOST «Smart» (TAS-IX)** — 3 ГБ SSD, 15 сайтов, 15 БД, безлимитный трафик, cPanel | ~104 550 сум/мес |
| Домен | gade.uz | ~27 000 сум/год (бесплатно при оплате хостинга на год) |
| SSL | AutoSSL / Let's Encrypt — бесплатно в составе тарифа | — |

Тариф Nano (500 МБ) не берём: `node_modules`, standalone-сборка, логи и локальные изображения в него не уместятся. Smart даёт запас на два контура (прод + `dev.gade.uz`) и на рост каталога.

### Среда исполнения

Приложение запускается через **Node.js Selector в cPanel** (Phusion Passenger на CloudLinux), Node.js 22 LTS, режим `production`.

```
cPanel / CloudLinux LVE
├── Passenger + Node.js 22   — приложение Next.js (output: 'standalone')
├── Apache/LiteSpeed         — HTTPS, отдача статики, gzip/brotli
├── PostgreSQL или MySQL     — база данных в cPanel (см. раздел «Где храним данные»)
├── Cron (cPanel)            — задания синхронизации с Bitrix, бэкапы, sitemap
└── ~/uploads                — изображения товаров, раздача напрямую веб-сервером
```

**Важные ограничения shared-хостинга, которые нужно учесть в архитектуре:**

- Passenger усыпляет приложение при простое. **Фоновые задачи нельзя строить на `setInterval` внутри процесса** — только внешний cron, который дёргает HTTP-эндпоинт (см. ниже)
- Redis на shared-тарифе нет. Кеш каталога — в памяти процесса (LRU) + ISR-кеш Next.js на диске; rate limiting — средствами веб-сервера и таблицей в БД
- Действуют лимиты LVE (память, CPU, число одновременных процессов). **До старта разработки запросить у поддержки aHOST точные лимиты тарифа Smart** и заложить их в нагрузочный тест
- Нет root, нет systemd, нет Docker

### Cron-задания в cPanel

Все периодические задачи выполняются штатным планировщиком cPanel. Каждый эндпоинт защищён секретным токеном в заголовке и идемпотентен.

| Расписание | Команда | Назначение |
|---|---|---|
| `*/5 * * * *` | `curl -s -H "X-Cron-Token: ***" https://gade.uz/api/cron/sync-stock` | Остатки из Bitrix |
| `*/15 * * * *` | `curl -s -H "X-Cron-Token: ***" https://gade.uz/api/cron/sync-prices` | Цены из Bitrix |
| `0 * * * *` | `curl -s -H "X-Cron-Token: ***" https://gade.uz/api/cron/sync-catalog` | Товары, категории, снятые с продажи |
| `*/2 * * * *` | `curl -s -H "X-Cron-Token: ***" https://gade.uz/api/cron/process-queue` | Очередь отправки заказов в Bitrix, ретраи |
| `0 3 * * *` | `~/scripts/backup.sh` | Дамп БД + архив uploads |
| `30 3 * * *` | `curl -s https://gade.uz/api/cron/sitemap` | Пересборка sitemap.xml |

Требования: время выполнения каждого задания — до 30 секунд (иначе разбивать на батчи), результат пишется в таблицу `sync_log`, ошибки дублируются в Telegram.

### Стек приложения

```

            + Tailwind CSS + shadcn/ui

Ошибки:     Sentry (облачный, бесплатный тариф — объём ошибок небольшой)
```

### Где храним данные — решение принято

**PostgreSQL, созданный средствами cPanel на том же хостинге.** aHOST поддерживает это штатно, доплаты к тарифу нет.

Почему так:

- Данные физически в Ташкенте, в сети TAS-IX — вопрос локализации персональных данных по закону №ЗРУ-547 закрыт
- Обращение к базе идёт по localhost, задержка ~1 мс вместо ~120 мс до зарубежного облака
- Ноль зависимости от внешнего сервиса: нет лимитов egress, нет риска, что магазин встанет из-за проблем у стороннего провайдера
- Входит в стоимость тарифа

Что это значит для разработки: собственного «бэкенда» как отдельного сервиса нет. Данные читаются напрямую в серверных компонентах Next.js через Drizzle ORM, запись и интеграции — в Route Handlers и Server Actions. Клиент к базе не обращается никогда, поэтому RLS-политики не нужны — разграничение прав делается в коде.

**Что придётся реализовать самостоятельно** (по сравнению с использованием готового BaaS):

| Модуль | Оценка | Комментарий |
|---|---|---|
| Авторизация по OTP | 2–3 дня | Auth.js + генерация кода, хеш в БД с TTL, лимит попыток, отправка через Eskiz.uz |
| Загрузка и обработка изображений | ~1 день | `sharp` → WebP в трёх размерах → `~/uploads` |
| Скрипт резервного копирования | полдня | `pg_dump` + архив `uploads` по cron, ротация 30 дней |

**Обязательные требования к работе с БД:**

- Слой доступа к данным изолирован (репозитории/сервисы) — смена БД или переезд на другой хостинг не должны расползаться по всему коду
- Миграции через Drizzle Kit, версионируются в репозитории, применяются только скриптом, руками в phpPgAdmin схему не правим
- Отдельный пользователь БД для приложения с минимально необходимыми правами
- Подключение задаётся одной переменной `DATABASE_URL`

**Наличие PostgreSQL проверено** (10.08.2026, сервер uz03.ahost.uz, cPanel 136.0.33). В панели доступны:

- `PostgreSQL Databases` и `PostgreSQL Database Wizard` — создание баз и пользователей
- `phpPgAdmin` — веб-интерфейс для просмотра данных
- `Remote Database Access` — на случай, если позже понадобится доступ к БД с другого сервера
- `Terminal` и SSH — миграции Drizzle прогоняются прямо на хостинге

**Что ещё уточнить тикетом в поддержку до начала работ:**

1. Версия PostgreSQL на сервере
2. Лимиты LVE для тарифа Smart: память, CPU, `nproc`, `entry processes` — цифры нужны для нагрузочного теста
3. Можно ли выполнить `CREATE EXTENSION pg_trgm` под пользователем базы. Начиная с PostgreSQL 13 это расширение помечено как trusted и создаётся владельцем БД без прав суперпользователя, но на конкретной сборке лучше убедиться заранее — от него зависит поиск с опечатками из п. 5.1

**Запасные варианты на случай упора в лимиты shared-хостинга:**

| Вариант | Когда применять | Доплата |
|---|---|---|
| Отдельный VDS Cloud 10/20 на aHOST под БД и Redis | При упоре в лимиты LVE или необходимости полноценной очереди | ~125–140 тыс. сум/мес |
| UzCloud — managed PostgreSQL | Если заказчик захочет формальные гарантии по хранению персональных данных, автобэкапы и failover | по запросу |

Оба варианта оставляют данные в Узбекистане и требуют только смены `DATABASE_URL`.

### ⚠️ Критично для TAS-IX: никаких внешних CDN

Если статику проксировать через Cloudflare или подключать внешние CDN, трафик пойдёт по внешнему каналу и **весь смысл TAS-IX пропадёт** — скорость упадёт, а у пользователей будет тратиться платный интернет-трафик. Поэтому:

- ❌ Не использовать Cloudflare proxy, jsDelivr, unpkg, Google Fonts CDN, внешние хранилища изображений
- ✅ Шрифты — самохостинг через `next/font/local`
- ✅ Все библиотеки — в бандле, ничего не подгружается со сторонних доменов
- ✅ Изображения — только со своего домена
- Допустимые исключения: скрипты аналитики (Метрика, Pixel) и callback-домены платёжных систем — они лёгкие и обязательны

### Деплой и эксплуатация

- Git-репозиторий (GitHub/GitLab), ветки `main` (прод) и `dev`
- **Сборка выполняется в CI (GitHub Actions), а не на хостинге** — `next build` под лимитами LVE непредсказуем по памяти. На сервер приезжает готовый `standalone`-артефакт
- Доставка на хостинг: Git Version Control в cPanel либо rsync/SSH, затем `Restart App` в Node.js Selector
- Возможность отката на предыдущий релиз: хранить 3 последних релиза в отдельных директориях и переключать симлинк
- `.env` только на сервере, вне `public_html`, в репозиторий не попадает
- **Бэкапы:** ежедневный дамп БД + архив `~/uploads` через cron в 03:00, хранение 30 дней; плюс штатный бэкап cPanel. Копия выгружается на внешнее хранилище. Восстановление обязательно проверить до запуска
- **Мониторинг:** внешняя uptime-проверка каждую минуту с алертом в Telegram (Passenger усыпляет приложение — «холодный» первый запрос нужно отслеживать); контроль занятого места, чтобы не упереться в 3 ГБ
- Тестовый контур: поддомен `dev.gade.uz` как второе приложение в Node.js Selector с отдельной БД (тариф Smart позволяет 15 сайтов)

### Требования к качеству кода

- Строгий TypeScript, никаких `any`
- Все цены хранятся в БД в тийинах (integer), форматируются на выводе
- Никаких секретов в клиентском коде; интеграции — только на сервере
- Разграничение прав в БД: отдельный ограниченный пользователь для приложения
- Мобильный трафик — приоритет: mobile-first вёрстка, Lighthouse Performance ≥ 90 на мобильном
- Агрессивное кеширование каталога через ISR — под лимитами shared-хостинга каждый лишний запрос к БД дорог
- Слой доступа к данным изолирован (репозитории/сервисы), чтобы смена БД или переезд на другой хостинг не расползались по всему коду

## 5. Функциональные требования

### 5.1 Каталог

- Иерархия: Категория → Линия бренда → Товар
- Фильтры: категория, линия, тип волос/кожи, ценовой диапазон, «в наличии», «со скидкой»
- Сортировка: популярные, новинки, цена ↑↓
- Поиск с подсказками по названию и линии, с учётом раскладки и опечаток — реализуется через `pg_trgm` (триграммное сходство) плюс транслитерация запроса латиница ↔ кириллица
- Пагинация или бесконечная лента — на усмотрение, но без потери позиции при возврате из карточки
- SEO-friendly URL: `/catalog/gade-hydra-shampoo-250ml`

### 5.2 Карточка товара

- Галерея изображений (минимум 1, до 6)
- Название, линия, объём, артикул
- Цена, старая цена и бейдж скидки при наличии
- Статус: «В наличии» / «Осталось мало» / «Нет в наличии» (из Bitrix)
- Описание, состав, способ применения, для какого типа волос/кожи — раскрывающиеся блоки
- Кнопки: «В корзину», «В избранное»
- Блок «С этим покупают» (4 товара)
- Микроразметка Schema.org Product + Offer

### 5.3 Корзина и оформление

- Корзина сохраняется в localStorage для гостя и синхронизируется с БД после входа
- Изменение количества, удаление, поле промокода
- **Оформление на одной странице, без шагов-визарда:**
  1. Имя + номер телефона (маска `+998 __ ___ __ __`)
  2. Способ доставки: курьер по Ташкенту / отправка в регион / самовывоз
  3. Адрес (для курьера) — с подсказками и картой
  4. Способ оплаты
  5. Комментарий к заказу (опционально)
  6. Кнопка «Оформить заказ»
- Подтверждение номера через SMS-код — только на этапе оплаты или для нового номера, чтобы не терять конверсию
- Экран «Спасибо» с номером заказа и кнопкой перехода в Telegram-чат поддержки

### 5.4 Оплата

Обязательные методы:

| Метод | Тип | Примечание |
|---|---|---|
| **Payme** | онлайн | Merchant API, приём и подтверждение платежа, обработка возвратов |
| **Click** | онлайн | Click Up / Merchant API |
| **Картой при получении** | офлайн | Курьер с POS-терминалом |
| **Наличными при получении** | офлайн | Ташкент, самовывоз |

Требования:

- Заказ создаётся до оплаты со статусом `pending_payment`; переход в `paid` только по callback от провайдера
- Все callback-эндпоинты — с проверкой подписи, идемпотентные (повторный callback не должен дублировать статус)
- Логирование всех платёжных транзакций в отдельную таблицу с сырым payload
- Для наличных и карты при получении — заказ сразу в статусе `confirmed`, оплата фиксируется вручную менеджером

### 5.5 Доставка

- Курьер по Ташкенту: тариф фиксированный, бесплатно от суммы заказа X (значение настраивается в админке)
- Отправка в регионы: расчёт по зонам, интеграция с курьерской службой опциональна на первом этапе — достаточно фиксированного тарифа по областям
- Самовывоз со склада: адрес, часы работы, карта

### 5.6 Личный кабинет

- Вход по номеру телефона + OTP
- История заказов со статусами
- Сохранённые адреса
- Избранное
- Данные профиля

### 5.7 Админ-панель

Минималистичная, для нетехнического менеджера. Всё на русском.

- Заказы: список, фильтр по статусу и дате, карточка заказа, смена статуса, печать накладной
- Товары: редактирование описаний, изображений, категорий, скидок, признака «хит»/«новинка» *(остатки и базовые цены приходят из Bitrix и не редактируются вручную)*
- Промокоды: код, процент/сумма, срок действия, минимальная сумма заказа, лимит применений
- Настройки: тарифы доставки, порог бесплатной доставки, контакты, тексты баннера, получатели Telegram-уведомлений
- Экспорт заказов в Excel

### 5.8 Уведомления о заказах — Telegram-бот

Помимо выгрузки в Bitrix, каждый заказ должен **немедленно приходить в Telegram**. Bitrix — это учёт, Telegram — оперативная реакция: менеджер видит заказ на телефоне и перезванивает клиенту в течение нескольких минут, не открывая CRM.

**Как работает**

- Отдельный бот, созданный через @BotFather; токен хранится в переменных окружения
- Сообщения отправляются в закрытую группу менеджеров (или канал), ID группы — в настройках
- Отправка идёт из очереди: если Telegram недоступен, сообщение повторяется, но **оформление заказа не блокируется и клиент ошибки не видит**

**Формат сообщения о новом заказе**

```
🛒 Новый заказ №1043
────────────────────
👤 Дилноза
📞 +998 90 123 45 67
────────────────────
1. GADE Hydra Shampoo 250 ml — 2 шт × 185 000 = 370 000
2. GADE Repair Mask 200 ml — 1 шт × 240 000 = 240 000
────────────────────
Доставка: курьер по Ташкенту, 25 000
Адрес: Мирабадский р-н, ул. Нукус 12, кв. 5
Оплата: Payme (оплачен) ✅
Комментарий: позвонить после 18:00
────────────────────
💰 Итого: 635 000 сум
🕐 10.08.2026, 14:32
```

Под сообщением — инлайн-кнопки: **«Принять в работу»**, **«Позвонить»** (ссылка `tel:`), **«Открыть в админке»**. Нажатие «Принять в работу» меняет статус заказа в БД и подписывает сообщение именем менеджера — чтобы двое не звонили одному клиенту.

**Какие ещё события уходят в Telegram**

| Событие | Куда | Зачем |
|---|---|---|
| Новый заказ | группа менеджеров | основной сценарий |
| Онлайн-оплата подтверждена | группа менеджеров | отдельным сообщением-ответом к заказу |
| Заказ отменён клиентом | группа менеджеров | — |
| Товар закончился на складе | группа менеджеров | по данным синхронизации |
| Ошибка синхронизации с Bitrix | технический чат | чтобы сбой не остался незамеченным |
| Ошибка платёжного шлюза | технический чат | — |
| Сайт недоступен (uptime-монитор) | технический чат | — |

**Требования**

- Telegram — резервный канал, а не единственный: заказ в любом случае сохранён в БД и поставлен в очередь на отправку в Bitrix
- Никаких данных банковских карт в сообщениях
- Список получателей и ID групп настраиваются в админке без правки кода
- Дублирующее SMS-уведомление покупателю через Eskiz.uz: подтверждение принятия заказа и сообщение о передаче курьеру

## 6. Интеграция с Bitrix — двусторонняя синхронизация

**Это критический модуль. Двойной учёт недопустим: Bitrix остаётся единственным источником правды по товарам, остаткам и ценам.**

### Направление Bitrix → Сайт

| Данные | Частота | Механика |
|---|---|---|
| Каталог товаров (название, артикул, категория, линия) | 1 раз в час | Инкрементально по дате изменения |
| Цены | каждые 15 минут | Перезапись |
| Остатки на складе | каждые 5 минут + вебхук при изменении | Перезапись |
| Статус «снят с продажи» | 1 раз в час | Скрытие товара с сайта |

### Направление Сайт → Bitrix

| Событие | Действие в Bitrix |
|---|---|
| Создан заказ | Создать сделку (или заказ в интернет-магазине) со всеми позициями, суммой, способом оплаты и доставки |
| Новый покупатель | Создать/найти контакт по номеру телефона, привязать к сделке |
| Оплата подтверждена | Обновить статус сделки, зафиксировать оплату |
| Заказ отменён | Перевести сделку в проигранные с причиной |

### Технические требования

- Синхронизация через **вебхуки Bitrix REST API** (входящие и исходящие)
- Все обращения к Bitrix — через сервисный слой с очередью и exponential backoff при ошибках
- Таблица `sync_log`: время, направление, сущность, статус, ошибка. Просмотр из админки
- **Сайт не должен падать, если Bitrix недоступен** — работает на последних закешированных данных, отправка заказов ставится в очередь и повторяется
- Маппинг ID: таблица соответствия `bitrix_id ↔ site_id` для товаров, категорий, клиентов и заказов
- Изображения товаров скачиваются из Bitrix на сервер при первой синхронизации, дальше — только при изменении хеша; сразу конвертируются в WebP в трёх размерах

### ⚠️ Уточнить у заказчика до старта разработки

1. **Какой именно Bitrix используется — Bitrix24 (облачная CRM) или 1С-Битрикс (CMS «Управление сайтом»)?** От этого зависит весь API-слой.
2. Есть ли доступ администратора для создания вебхуков и приложений?
3. Ведутся ли остатки по нескольким складам, или склад один?
4. В каком виде хранятся товары — в CRM-каталоге, в торговом каталоге или в списках?
5. Есть ли уже связка Bitrix ↔ 1С, и не сломает ли встречная запись существующие процессы?

## 10. Этапы работ

**Этап 1 — MVP (3–4 недели)**
Каталог, карточка, корзина, оформление, оплата Payme + Click + наличные, базовая админка, Telegram-уведомления о заказах, односторонняя выгрузка каталога из Bitrix.

Двусторонняя синхронизация с Bitrix, живые остатки, отправка заказов в CRM, очередь и мониторинг.

Личный кабинет, квиз «Подбор ухода», промокоды, избранное, узбекская локализация, SEO-донастройка.

**Этап 4 — Запуск**
Нагрузочное тестирование на боевой конфигурации, проверка восстановления из бэкапа, наполнение контентом, обучение менеджера, передача документации по эксплуатации сервера.
