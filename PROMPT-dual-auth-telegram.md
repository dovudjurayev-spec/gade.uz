# Задача: два способа входа — email на сайте, Telegram-аккаунт в мини-аппе (gade.uz)

Одна и та же база пользователей, два способа аутентификации:
- **веб-сайт** — email + пароль, как сейчас, ничего не ломаем;
- **Telegram Mini App** — автоматический вход по `initData`, без пароля и без ввода email.

Один покупатель может иметь оба идентификатора и должен видеть одни и те же заказы, избранное и адреса
независимо от того, откуда зашёл.

## Что уже есть в проекте
- `src/lib/customer-auth.ts` — scrypt-хэш пароля, сессии в таблице `sessions`, кука `gade_customer`
  (`httpOnly`, `sameSite: "lax"`, `secure` в проде, TTL 30 дней), `getCurrentCustomer()`,
  `createCustomerSession()`, `destroyCustomerSession()`, сброс пароля по токену.
- `src/app/api/auth/login|logout|register|register/verify|password/*` — вход, регистрация с подтверждением
  email через Resend, сброс пароля. Везде rate limit из `src/lib/rate-limit.ts`.
- `customers` (`src/db/schema.ts`): `phone`, `name`, `email`, `password_hash` — все nullable, уникальные
  частичные индексы на `phone` и `email`.
- `getCurrentCustomer()` используется в `account/(protected)/**`, `checkout`, `api/favorites`,
  `payment/[number]`, `checkout/success/[number]` — список проверь сам, он может вырасти.
- Telegram уже подключён, но как **админский** бот уведомлений о заказах (`@gadeuzbot`,
  `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ORDERS_CHAT_ID`, `src/app/api/telegram/webhook/route.ts`).

## 1. Схема
В `customers` добавить (аддитивная миграция, ничего не удалять):
- `telegram_id` bigint — id пользователя Telegram;
- `telegram_username` varchar(64);
- `telegram_photo_url` text;
- частичный уникальный индекс: `UNIQUE (telegram_id) WHERE telegram_id IS NOT NULL` — по образцу
  существующих индексов на `phone` и `email`.

Отдельную таблицу identities не заводим: провайдера всего два. Если позже появится Google/Apple —
вынесем в `customer_identities (provider, external_id)`, но не сейчас.

Аккаунт, созданный из Telegram, имеет `email = NULL` и `password_hash = NULL`. Это допустимое состояние,
схема его уже позволяет — но код местами может это не ожидать, см. пункт 5.

## 2. Проверка initData
Новый модуль `src/lib/telegram-auth.ts`, чистая функция без обращений к БД:

```
validateInitData(initData: string, botToken: string, maxAgeSec: number)
  → { ok: true, user: { id, first_name, last_name?, username?, photo_url?, language_code? }, authDate: Date }
  | { ok: false, reason: "bad_format" | "bad_hash" | "expired" | "no_user" }
```

Алгоритм строго по документации Telegram:
1. распарсить `initData` как query string;
2. вынуть и удалить поля `hash` и `signature`;
3. собрать `data_check_string` — оставшиеся пары `key=value`, отсортированные по ключу, склеенные через `\n`;
4. `secret_key = HMAC_SHA256(key: "WebAppData", data: botToken)`;
5. `computed = HMAC_SHA256(key: secret_key, data: data_check_string)`, сравнить с `hash` через
   `crypto.timingSafeEqual` (не через `===`);
6. проверить `auth_date`: не старше `maxAgeSec` — для входа поставить **3600 секунд**, не 24 часа;
7. только после успешной проверки подписи распарсить JSON из поля `user`.

Категорически: `user.id` из клиентского JSON не используется, пока подпись не проверена.

Токен бота — отдельная переменная `TELEGRAM_TMA_BOT_TOKEN` в `src/lib/env.ts` (может совпадать по значению
с `TELEGRAM_BOT_TOKEN`, но переменная отдельная: мини-апп и админ-уведомления не должны быть связаны).
Добавить её в `.env.example` с комментарием.

## 3. Эндпоинт входа
`POST /api/auth/telegram`, `runtime = "nodejs"`, тело `{ initData: string }`:
- rate limit по IP и по `telegram_id` (по образцу `login/route.ts`);
- `validateInitData(...)`; при неудаче — 401 и запись в лог с причиной, без деталей в ответе;
- ищем `customers` по `telegram_id`:
  - нашли → `createCustomerSession(customer.id)`, обновляем `telegram_username` / `telegram_photo_url` /
    `name`, если они изменились;
  - не нашли → создаём: `telegram_id`, `name` = `first_name` + `last_name`, `telegram_username`,
    `email = NULL`, `password_hash = NULL`, затем сессия;
- ответ `{ ok: true, sessionToken }` — про `sessionToken` см. следующий пункт.

## 4. Сессия в webview — куки недостаточно
На мобильных клиентах мини-апп открывается в webview и кука работает. Но в Telegram Web мини-апп — это
iframe на стороннем домене, и `SameSite=lax` кука туда не долетит, а Safari может резать и `SameSite=None`.
Поэтому сессия должна ездить двумя путями:
- кука `gade_customer` — как сейчас, но для запросов из мини-аппа выставлять `sameSite: "none"` **вместе с**
  `secure: true` (иначе браузер отклонит куку целиком); в дев-режиме по http это работать не будет — учти
  и опиши, как тестировать (туннель с https);
- плюс тот же идентификатор сессии возвращать в теле ответа как `sessionToken`, клиент мини-аппа хранит его
  в памяти/`sessionStorage` и шлёт заголовком `Authorization: Bearer <token>`.

`getCurrentCustomer()` расширить: сначала кука, если её нет — заголовок `Authorization: Bearer`.
Контракт возвращаемого объекта не ломать, только добавить поле `telegramId`. Формат токена — тот же
`sessions.id`, никаких JWT.

## 5. Места, где код предполагает наличие email
Найди и почини все — минимум:
- `account/(protected)/**` — профиль должен нормально отображаться при `email = NULL` и предлагать
  «Привязать email», а не показывать пустое поле;
- отправка писем через Resend (подтверждение заказа и т.п.) — если `email` пустой, письмо не отправляем,
  а не падаем; для заказа из мини-аппа уведомление уходит в Telegram;
- сброс пароля и вход по email для аккаунта без пароля должны отдавать понятную ошибку, а не 500;
- `checkout` — имя предзаполняем из Telegram, телефон всё равно спрашиваем (он нужен курьеру).

## 6. Связывание аккаунтов
Автоматическое слияние по имени, телефону или email — запрещено. Telegram не отдаёт email, а совпадение
телефона не доказывает, что это тот же человек.

Два явных сценария, оба через действие пользователя:
- аккаунт создан в Telegram, пользователь хочет заходить и на сайте: в личном кабинете кнопка
  «Добавить вход по email» → форма email + пароль → тот же `customer.id` получает `email` и `password_hash`
  (email подтверждаем существующим флоу `register/verify`);
- у пользователя уже есть email-аккаунт, и он впервые открыл мини-апп: он попадает в новый TG-аккаунт,
  но в интерфейсе есть «У меня уже есть аккаунт» → вход по email и паролю → после успешного входа
  `telegram_id` привязывается к **существующему** customer, а пустой только что созданный TG-аккаунт удаляется
  (или, если к нему уже успели привязаться заказы, — не удаляется, а помечается; опиши выбранное поведение).

Если `telegram_id` уже занят другим аккаунтом — отказ с внятным текстом, без перезаписи.

## 7. Тесты
Обязательно юнит-тесты на `validateInitData` с фикстурами, сгенерированными от известного тестового токена:
- валидный initData — проходит;
- подделанный `hash` — отклоняется;
- изменённое поле `user` при правильном старом `hash` — отклоняется;
- `auth_date` старше часа — отклоняется;
- отсутствующий `hash` или `user` — отклоняется;
- сравнение хэшей идёт через `timingSafeEqual`.

Сценарные проверки: первый вход из Telegram создаёт ровно один аккаунт; повторный вход второй не создаёт;
привязка email к TG-аккаунту работает; вход по email на сайте после всех изменений работает как раньше;
выход (`/api/auth/logout`) убивает сессию в обоих случаях.

## 8. Ограничения
- Существующий вход по email не ломать ни в одном сценарии — это прод, там живые покупатели.
- Миграция только аддитивная, ничего не удалять и не делать NOT NULL.
- Работать в отдельной ветке `feat/telegram-auth` от main. Ветку `wip/catalog-l2-grouping` не трогать,
  с работой по категориям не смешивать.
- **Не деплоить на прод с 29 августа по 1 сентября** — выходные на День независимости Узбекистана,
  поддержка Payme и Click недоступна, а это пик заказов. Либо до конца 28 августа, либо после 2 сентября.
- Секреты не логировать: ни токен бота, ни `initData` целиком, ни `sessionToken`.
- Комментарии и UI по-русски, коммиты по-английски.

Порядок: сначала покажи план файлов и миграцию на утверждение, потом `src/lib/telegram-auth.ts` с тестами
отдельным коммитом, потом эндпоинт и правки сессии, и только в конце — правки UI личного кабинета
и связывание аккаунтов. После каждого шага останавливайся и показывай диф.
